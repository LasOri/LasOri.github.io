### Long Story Short
Mimic is a Swift testing framework I created while working at [Emarsys](https://emarsys.com/). The problem was simple: writing mocks in Swift is tedious. The language has limited runtime reflection, so most solutions rely on build scripts, code generation tools, or a lot of manual boilerplate.

So I built a small framework that generates fake classes at compile time using Swift macros, provides a `when`/`verify` API for stubbing and verification, and has a `@Generate` property wrapper that creates `Decodable` instances without any manual setup. It started as a tool for the team's internal SDK development.


### How Does It Work?
Mimic has three parts: **mocking**, **verification**, and **instance generation**.

#### Mocking with `@Fakeable`
You annotate a protocol with `@Fakeable`, and a Swift macro generates a fake class at compile time.

```swift
@Fakeable
protocol UserService {
    var currentUser: String { get }
    func login(username: String, password: String) throws -> Bool
    func logout() throws
}
```

This generates a `FakeUserService` class with `Fn<T>` properties for each method and computed property. The macro parses the protocol using swift-syntax, extracts methods, properties, return types, and effect specifiers like `async` and `throws`, then builds the class.

The generated code looks something like this:
```swift
final class FakeUserService: UserService, Mimic {
    public let fnLogin = Fn<Bool>()
    public let fnLogout = Fn<()>()
    public let fnCurrentUserGetter = Fn<String>()

    func login(username: String, password: String) throws -> Bool {
        return try fnLogin.invoke(params: username, password)
    }
    func logout() throws {
        try fnLogout.invoke()
    }
    var currentUser: String {
        try! fnCurrentUserGetter.invoke()
    }
}
```

No build scripts, no separate code generation step.

#### Stubbing with `when`
Once you have a fake, you configure its behavior through a `when` API. It uses KeyPaths to reference `Fn` properties, so it's type-safe.

```swift
let fakeService = FakeUserService()

// Simple return
fakeService.when(\.fnLogin).thenReturn(true)

// Sequential returns
fakeService.when(\.fnLogin).thenReturns(true, true, false)

// Conditional with matchers
fakeService.when(\.fnLogin)
    .calledWith(Arg.eq("admin"), Arg.any)
    .thenReturn(true)

// Exception throwing
fakeService.when(\.fnLogin)
    .thenThrow(error: AuthError.invalidCredentials)
```

There's also `replaceFunction` for when you need full control over the invocation count and parameters:
```swift
fakeService.when(\.fnLogin)
    .replaceFunction { invocationCount, params in
        let username: String = params?[0] ?? ""
        return username == "admin"
    }
```

#### Verification with `verify`
After running the code under test, you verify what happened:

```swift
// Verify it was called exactly once
try fakeService.verify(\.fnLogin).times(times: .eq(1))

// Verify with specific arguments
try fakeService.verify(\.fnLogin)
    .wasCalled(Arg.eq("admin"), Arg.eq("secret"))
    .times(times: .atLeast(1))

// Verify it was never called
try fakeService.verify(\.fnLogout).times(times: .zero)
```

You can also verify which thread a function was called on:
```swift
try fakeService.verify(\.fnLogin).on(thread: Thread.main)
```

This was useful for us when testing the SDK—ensuring callbacks were dispatched on the correct thread was a recurring issue.

#### Argument Captor
Sometimes you need to inspect the actual values passed to a function. That's what `ArgumentCaptor` is for:

```swift
let captor = ArgumentCaptor<String>()

fakeService.when(\.fnLogin)
    .calledWith(captor.capture(), Arg.any)
    .thenReturn(true)

_ = try fakeService.login(username: "hello", password: "world")
_ = try fakeService.login(username: "admin", password: "secret")

captor.values      // ["hello", "admin"]
captor.firstValue  // "hello"
captor.lastValue   // "admin"
```


### The Instance Generator
The mocking part of Mimic is nothing new—there are other frameworks that solve the same problem, like [Cuckoo](https://github.com/Brightify/Cuckoo) with its build-script-based code generator. The `@Generate` part is a bit more unusual.

The problem: you have a `Decodable` struct with ten or twenty fields, and you need an instance of it in your test. You don't care about most of the values. But Swift won't let you skip fields, so you end up writing factory methods or long initializers filled with dummy values.

`@Generate` handles this with a single annotation:
```swift
@Generate
var user: User
```

You get a `User` instance with random values for every field. If you need specific values for certain properties, you pin them:
```swift
@Generate([
    \User.name: "Laci",
    \User.isActive: true
])
var specificUser: User
```

Everything else gets random data. The predefined values use `PartialKeyPath`, so the compiler checks that the property actually exists on the type.

#### How Does It Work Under the Hood?
The approach is a bit hacky, to be honest, but it works.

It starts with an empty JSON object and tries to decode it into the target type. This fails because the struct has required fields. But the `DecodingError` that Swift throws tells us which key is missing and what type was expected. Based on this, we generate the value, add it to the JSON, and try again.

```swift
var result: T? = nil
var json = Json.object([:])
repeat {
    do {
        let jsonData = try encoder.encode(json)
        result = try decoder.decode(T.self, from: jsonData)
    } catch DecodingError.typeMismatch(let type, let context) {
        let value = try encodable(encodables, type) ?? jsonFactory.create(type)
        json[context.codingPath] = value
    } catch DecodingError.keyNotFound(let codingKey, let context) {
        var paths = context.codingPath
        paths.append(codingKey)
        let value = try predefinedValue(predefinedValues, paths.first!)
            ?? Json.string(StringGenerator().generate())
        json[paths] = value
    }
} while result == nil
```

Each iteration fills one more field. A `keyNotFound` means a field is missing—we add a predefined or random value. A `typeMismatch` means the type is wrong—we fix it. The loop runs until the decoder accepts the JSON.

This handles nested structs, arrays, and dictionaries without any special logic. The decoder reports missing keys at deeper coding paths, and the `Json` enum's subscript handles nested insertion recursively.

```swift
// Works with nested types, arrays, and dictionaries
@Generate(encodables: SomeEnum.case1("text", 42))
var complexModel: ComplexModel
```

For custom types like enums that can't be randomly generated, you pass them as `encodables`. The generator matches them by type using reflection and uses them when needed.

#### Is There Anything Similar?
I looked around for existing solutions to this specific problem. [Fakery](https://github.com/vadymmarkov/Fakery) generates fake primitives—names, emails, phone numbers—but you still have to wire them into your structs manually. [SwiftCheck](https://github.com/typelift/SwiftCheck) generates random data for property-based testing, but it requires every type to conform to the `Arbitrary` protocol.

`@Generate` requires nothing extra from the type—just `Decodable`, which most model types already conform to. I haven't found another library that does this the same way, but I might have missed something.


### Why Is It Ugly?
The `@Generate` property wrapper relies on the internal behavior of Swift's `Decoder`. It catches `DecodingError.keyNotFound` and `DecodingError.typeMismatch` to figure out what the struct needs, and there's no guarantee those error messages won't change in a future Swift version. Many recommendations and principles, like SOLID or the Law of Demeter, state that you **should not do this**, and I totally agree. This is why I don't recommend using it in production code.

On the other hand, its functionality to create a whole complex model for testing purposes with only an annotation is handy enough to use during testing—at least in my opinion.

The generated fake classes use `try!` for non-throwing protocol methods. If you forget to configure a `when` before a function gets called, you get a runtime crash. Not ideal, but making every protocol method throwing just for the mock felt worse.

`@Fakeable` only works with protocols—you can't fake a concrete class. That's by design. It pushes you towards protocol-oriented design, which is where Swift wants you to be anyway.


### How Could It Be Better?
- If Swift exposed the property names and types of `Decodable` structs through a public API, `@Generate` wouldn't need to rely on error parsing at all.

- The matchers are fairly basic: `Arg.eq`, `Arg.any`, `Arg.nil`, `Arg.notNil`, and `Arg.invokeClosure`. A custom matcher protocol exists so you can extend it, but out of the box it doesn't compare to something like Hamcrest.

- Thread verification checks if all invocations happened on the expected thread, but doesn't support things like "the first call was on main, the second on a background queue."

- `@Generate` regenerates a new instance on every property access. This is intentional—each test gets fresh data—but if you need the same instance twice, assign it to a local variable first.


### Why I Leave It As It Is (At Least for Now)
For me, Mimic was a practical project to solve a recurring annoyance in our daily testing work. To be honest, since it satisfies what we need, I don't feel the urge to change it—at least not until a new issue comes along that inspires me to do so.

The Swift macro system keeps evolving, and if it ever introduces something that makes the `@Generate` approach less fragile, that would be a good reason to revisit it.


### What Is the Lesson from All of This?
If you can't find a library that satisfies your needs, consider creating one yourself because it can be fun. If you need to make compromises, do so, but always keep them in mind and make sure to warn about them in the documentation. The best solution is not always the nicest; it's the one that solves your issues.
